# 振り分けた依頼を実行する仕組み 設計

2026-11-21、2026-11-22 に案 A へ改訂。前提は `docs/journal-triage-design.md`（分類器）。

## この設計で使う語

- 依頼 = 分類器が `action:<種類>` と判定した発話
- 例外 = 人が見てからでないと送ってはいけない依頼。条件は「例外になる条件」で決める
- 猶予 = 送る前の待ち時間。既定は 5 分で、その間なら取り消せる
- 送り先 = 依頼の種類ごとに設定する送り方（URL を開く、POST、コマンド）。今の `macOS.actions` と同じ形
- 送り先の重さ = 送った後に取り消しやすいか。`heavy: true` の送り先は重い（既定は重い）

## 目標と問題

- 目標: 話した依頼が実行まで進み、Python やターミナルを使わない人も voice-switch を入れるだけで使える。Mac と Windows で同じに動く。
- 問題: 今の分類はターミナルに一覧を出して終わる。実行する手段も、承認する画面も無い。Python のスクリプトなので、アプリから呼べず、配りにくい。

## 実行のきっかけの比較

| 候補 | 安全性 | 配りやすさ | 両 OS の手間 |
|---|---|---|---|
| メニューバーの提案画面で承認して実行 | 高い。#50 の「提案は自動、実行は承認制」をそのまま満たす | 高い。アプリに入っている | 分類器と画面を Swift と C# の両方に作る |
| 自動実行 | 低い。誤分類がそのまま外へ出る | 高い | 上と同じ実行部分を使えば、増えるのは印の判定だけ |
| 専用 CLI | 中くらい。承認の画面が無い | 低い。開発者向け | Python 1 本で済む |

## 採った形: 猶予つきの自動送信と、例外だけの確認（案 A、2026-11-22）

確かな依頼は猶予の後に自動で送り、人が見るのは例外だけにする。件数が増えても操作は増えない。送るやり方は 1 つで、自動で送るときも人が押したときも、同じ実行部分（今の `WakeAction` の open / post / command）を通る。

比べて採らなかった形は 2 つある。案 B（1 時間ごとなどに送り先ごとの束を承認する）は、押す回数は少ないが届くのが遅れる。案 C（すぐ送って、あとで取り消す）は、重い送り先では取り消せないことがある。

### 画面（メニューバーから開く 1 枚）

```
voice-switch  依頼                               [一時停止]
─────────────────────────────────────────────
確認が要るもの (2)
  ? 来週の分を調べて                    種類が迷い
      → [調べもの] [PC への変更] [送らない]
  ! 古いブランチを全部消して            重い送り先
      → エージェント           [送る] [送らない]
─────────────────────────────────────────────
まもなく送る (3)                          [すぐ送る]
  4:52  牛乳を買っておかないと          → changelogmemo  [取消]
  4:10  天気を調べられるようにして      → エージェント    [取消]
─────────────────────────────────────────────
送った (今日 12)  ▸                    （開くと履歴と [種類を直す]）
```

- メニューバーのアイコンには、例外の件数だけを出す。
- 「確認が要るもの」は、例外の理由（種類が迷い、重い送り先、初めての送り先、続けての依頼）を行ごとに出す。種類のボタンを押すと、その種類で送る。
- 失敗した依頼も「確認が要るもの」に理由つきで出す。[やり直す] で同じ送り先へ送り、[送らない] で確認から外す。送り先の設定が変わった場合は [やり直す] を無効にする。
- 「まもなく送る」は、残り時間と送り先を出す。[取消] で送らない。[すぐ送る] は猶予を待たずに送る。
- 「送った」は今日の履歴。[種類を直す] はラベルとして保存し、精度改善の正解にする。送ったものは取り消さない（取り消しは送り先の側で行う）。

### 例外になる条件（コードで判定し、どれか 1 つで例外）

1. 7 問のどれかの答えが「迷い」の帯にある、または種類が 2 つ以上「はい」。（種類が 1 つに決まったうえで、ほかの答えが迷いの帯にあるだけなら、重い送り先のときだけ例外にする。2026-11-22）
2. 依頼の種類に送り先が設定されていない。
3. 送り先が重い。重い送り先へ送る前に、Jev にもう 1 問聞く（「この本文をこの送り先へ送ると、話し手の望みどおりになるか」）。答えが 0.7 未満なら例外。
4. その送り先へ送るのが最初の 5 件のうち（慣らし期間）。（重い送り先だけに当てる。取り消しやすい送り先（heavy: false）には慣らし期間を置かない。2026-11-22）
5. 直前の 60 秒に、同じ送り先への依頼がある（言い直しによる重複の疑い）。

### 流れ（起きる順）

1. 発話が履歴に入り、ジャーナルに書かれる（今のまま）。
2. 一覧に出る行（配送先が history か null）なら、アプリが裏で分類器を動かす。録音と次の入力は待たせない。直前 60 秒の発話はメモリの履歴から取る。
3. 依頼で、例外の条件に 1 つも当てはまらなければ、「まもなく送る」に入れ、締め切り（今 + 猶予）と一緒に `proposals.jsonl` へ追記する。例外なら「確認が要るもの」に入れ、理由と一緒に追記する。`unjudged` と送り先の無い種類を CLI の一覧だけに残すと、メニューだけを使う人には見えず、依頼が黙って消えるため（`NoSilentDrop`）。
4. 締め切りが来た「まもなく送る」の行は、自動で送る。[取消] された行は送らない。
5. 「確認が要るもの」の行は、利用者が種類のボタンか [送る] を押したときだけ送る。[送らない] なら送らない。
6. 送り先を動かす直前に、`proposals.jsonl` へ「送信中」を追記する。コマンドと `open` は終了コード 0、POST は HTTP 2xx で「送った」を追記する。起動や通信のエラー、コマンドの終了コード 75 などの場合は理由と一緒に「失敗」を追記し、「確認が要るもの」に出す。ログに `triage: <id> failed <kind> <理由>` を出す。理由は終了コードや HTTP 状態などに限る。
7. 起動時に `proposals.jsonl` を読む。「まもなく送る」の行は、残っている締め切りのまま待つ。最後の行が「失敗」なら理由と一緒に「確認が要るもの」に戻す。「送信中」の依頼は「送ったか不明」として同じ欄に出す。失敗と送信結果が不明な依頼は、利用者が [やり直す] を選んだときだけ再送する（`AtMostOnce`）。結果が不明な依頼では [送ったことにする] も選べる。

### 設定（例）

```json
"dictation": {
  "triage": {
    "enabled": true,
    "graceSeconds": 300,
    "routes": {
      "self_task":       {"command": "scripts/memo-inbox-add task", "heavy": false, "graceSeconds": 60},
      "write_text":      {"command": "scripts/memo-inbox-add draft", "heavy": false},
      "look_up":         {"url": "grokbot://prompt?text={text}"},
      "computer_change": {"command": "<エージェントへ依頼するコマンド>"}
    }
  }
}
```

- 送り先の書き方は `macOS.actions` と同じ（`url`、`tokenEnv` 付きの POST、標準入力で本文を受ける `command`）。読み込みと検証のコードもそれを使う。
- `heavy` の既定は true。取り消しやすいと分かっている送り先だけ false にする。
- `graceSeconds` は全体の既定（300）と、送り先ごとの上書き。
- `enabled` が false なら、分類器は動かず、Jev にも何も送らない。

### 持ち主

| 状態 | 持ち主 | 書く人 |
|---|---|---|
| 発話の原文 | ジャーナル | アプリ（今のまま） |
| Jev の答え | 端末ごとのキャッシュ | アプリの分類器 |
| 依頼の状態（まもなく送る＋締め切り・確認が要るもの＋理由・送信中・送った・失敗・取消・送ったか不明） | `~/Library/Application Support/voice-switch/proposals.jsonl`（Windows は `%LOCALAPPDATA%\voice-switch\`）。追記だけで、id ごとの最後の行が今の状態 | アプリだけ |
| ラベル | `<root>/.triage/labels/<端末>-app.jsonl` | アプリの画面（[種類を直す] と例外での種類の選択）だけ |
| ラベル（まとめて付けるとき） | `<root>/.triage/labels/<端末>-cli.jsonl` | CLI の `review` だけ |
| しきい値 | `<root>/.triage/thresholds.json` | CLI の `tune --apply` だけ |
| 問いの文面 | `Resources/triage_questions.json`（1 つのファイル） | 人が編集する。Swift・C#・Python が同じファイルを読む |

### 3 つの言語でそろえるもの

- 問いの文面は JSON 1 つにして、Swift・C#・Python が読む。今の `scripts/triage_questions.py` はこの JSON に移す。
- 真理値表は Swift と C# と Python の 3 か所に書くことになる。`tests/parity/fixtures/triage_decide.json` に「答え → 行き先」の見本を全組み合わせで置き、3 つが同じ結果を出すことを確かめる（今の `pane_route.json` と同じ作り）。

### CLI の役目

`scripts/journal_triage.py` は、AI エージェントが呼ぶための入口にする（2026-11-21 決定）。担当は、まとめての見直し（`review`）、精度の計測（`eval`）、しきい値の調整（`tune`）、問いの比較（`eval --candidate`）。出力は機械が読める JSON を既定にし、人向けの表示は `--format text` で出す。実行はしない。利用者は使わなくてよい。

## 作業依頼と送り先の候補（2026-11-22 追加）

決めたこと（利用者、2026-11-22）

1. 種類に「作業依頼（`delegate`）」を足す。bot に処理を頼む依頼で、記録の書き換え、予定の登録、手順の実行など、頼んだ結果として何かが変わるもの（例「タスクシュートの夕食のタスクの開始を 19 時、終了を 20 時 15 分にして」）。調べもの（情報を知りたい）とも、PC への変更（PC の設定・コード・ファイルを変えたい）とも分ける。
2. 送り先は、種類ごとに候補を並べられる。先頭が自動送信のときの既定。既定は 作業依頼 = [Muse, Grok Bot]、調べもの = [Grok Bot, Muse]。
3. Muse へはメールで送る。宛先は `takets@muse.ai`。届くと Muse 側で処理が始まる。macOS のメール.app から osascript で送る（新しい鍵やパスワードを持たない）。

流れの変わるところ

1. 分類の問いに `kind_delegate` を足す。真理値表は今の `kind_*` と同じ扱い（「はい」をすべて採る）。
2. 「確認が要るもの」では、種類のボタンの代わりに、送り先の候補ごとのボタンを出す（[Muse に送る] [Grok Bot に送る]）。種類が決まらない依頼は、まず種類を選び、続けて送り先を選ぶ。
3. 「まもなく送る」の行は、送り先を表示し、猶予の間なら別の候補に替えられる。猶予が過ぎたら、表示中の送り先に送る。
4. `proposals.jsonl` に、選んだ送り先を記録する。再起動後も同じ送り先のまま。
5. 自動送信の例外の条件（重い送り先、最初の 5 件、60 秒以内）は、送り先ごとに数える。
   猶予中に替えた候補で例外に当てはまる場合は、確認に回る。重い候補への切り替えも確認に回る。
   例外がなければ、切り替えた候補の設定で猶予を数え直す。

設定（例）

```json
"routes": {
  "delegate": [
    {"name": "Muse（メールで頼むとタスクを処理する AI アシスタント）", "command": "scripts/mail-send takets@muse.ai", "heavy": false},
    {"name": "Grok Bot（AI アシスタント）", "url": "grokbot://prompt?text={text}"}
  ],
  "look_up": [
    {"name": "Grok Bot（AI アシスタント）", "url": "grokbot://prompt?text={text}", "heavy": false},
    {"name": "Muse（メールで頼む AI アシスタント）", "command": "scripts/mail-send takets@muse.ai", "heavy": false}
  ]
}
```

- 1 つの送り先だけを書く今の形（オブジェクト 1 つ）も、候補 1 つとして読む。
- `scripts/mail-send <宛先>` は、標準入力の本文の 1 行目を件名、全文を本文にしてメール.app から送る。送れなければ 0 以外で終わり、依頼は「送信に失敗」になる。

## 中身のある発話はまずメモに残す（2026-11-22 追加）

1. フィラーでない発話は、依頼かどうかに関係なく `dictation.triage.memo` の送り先にすぐ追記する（「考え」、依頼かどうかの迷い、内容の迷い、種類の迷い、重い送り先への依頼）。自分の作業と下書きは、その送り先がメモなので重ねて追記しない。
2. 依頼かどうかの迷いと内容の迷いは、確認に回さず「考え」として扱う。「メモしておいて」のように、考えを残してほしい発話が「依頼か」の問いで割れるため。
3. メモは提案の行を作らない。記録のための追記で、失敗したときは `triage: <id> memo failed <理由>` を 1 行出す。
4. 重い送り先へは、これまでどおり依頼であることと種類がはっきりしたときだけ送る。

## 守る規則（検証項目）

- E1 利用者が押したか、「まもなく送る」で猶予を最後まで待ったものしか送らない（`NoSendWithoutChance`）。
- E2 誤判定のまま送られるのは、猶予の間に誰も止めなかったときだけ（`NoWrongExecution`）。これが案 A の代償で、`risk.cfg` の `StrictNoWrongExecution` が反例を示す。
- E3 重い送り先へ自動で送るのは、追加の確認が通ったときだけ（`HeavyNeedsVerify`）。
- E4 取消・[送らない] にした依頼は、どの順で操作しても送られない（`DismissedNeverRuns`）。
- E5 同じ依頼は、利用者が「やり直す」を選ばない限り 1 回しか送られない。再起動、猶予切れと [すぐ送る] の重なりを含む（`AtMostOnce`）。
- E6 `unjudged`、送り先の無い種類、失敗した依頼は「確認が要るもの」に出る（`NoSilentDrop`）。
- E7 `enabled` が false なら、Jev への送信は 0 件。
- E8 送るのは既存の実行部分だけを通る。
- E9 意図した送り先と異なる送り先へ送られるのは、その送り先が「まもなく送る」に表示されたまま、誰も替えずに猶予が過ぎた場合だけ。利用者が送り先を選んだ依頼（猶予中の替え、[<name> に送る]）は、選んだ送り先にだけ送る（`NoWrongDestination`）。

E1〜E6 と E9 は `.claude/skills/verify-triage-execution`（TLA+）で検査する。2026-11-21 の承認制の設計では E5 と E6 が反例で破れ、流れ 3・6・7 を足した。2026-11-22 に案 A へ変えたとき、E1〜E3 を足した。

## 進める順

1. 問いの文面を JSON に移し、真理値表の共通見本を作る。Python の分類器をそれに合わせる（今のプローブも動くまま）。
2. Mac: 分類器をアプリに入れ、画面の「確認が要るもの」と「送った」、例外の判定、送信を作る。最初は全部の送り先を例外として扱い（慣らし期間を無限にする）、E1〜E8 を確かめる。
3. Mac: 「まもなく送る」と猶予つきの自動送信を有効にする。
4. Mac: 「送った」の [種類を直す] からラベルを付けられるようにする。
5. Windows に移す。共通見本で Swift と同じ結果を確かめる。

## 決めたこと

1. 形は案 A（猶予つきの自動送信と、例外だけの確認）。猶予の既定は 5 分（2026-11-22）。CLI は AI エージェントが呼ぶ入口にする（2026-11-21）。
2. 自分の作業（self_task）と下書き（write_text）の行き先は changelogmemo。ただし voice-switch は changelogmemo を直接書かず、取り込み待ちファイルに追記する（2026-11-22、下の「changelogmemo への取り込み」）。調べもの（look_up）と PC への変更（computer_change）の実行先は未定。
3. Mac を先に作る。Windows はあとで移す。

## changelogmemo への取り込み

どのファイルも、書き手を 1 つにする。

1. voice-switch の送り先 `scripts/memo-inbox-add` は、`~/repos/changelog/voice-switch-inbox.jsonl`（`VOICE_SWITCH_MEMO_INBOX` で変えられる）に JSON を 1 行追記するだけ。中身は id、at、kind、title、text。追記だけなので、前の行は変わらない。書けなければ 0 以外で終わり、依頼は「送信に失敗」になる。
2. 取り込み待ちファイルは、changelogmemo の写しの元として残す。memo-inbox-add は追記のあとに memo-import を呼び、changelogmemo にまだ無い id の行を、日付の行の下に新しい順で足す（2026-11-22、changelog スキルを動かさない限りメモが changelogmemo に現れなかったため）。changelog スキルも同じ規則で取り込む。
   - changelogmemo の書き手は 2 つになる。memo-import は読んでから置き換えるまでに相手が書いたら読み直すが、エディタが古い内容で上書きすると項目が一時的に消える。消えた項目は取り込み待ちファイルに残っており、次の取り込みで戻る（id で見分けるので二重にはならない）。下の 3 との違いは、元の行が消えないこと。
3. 2026-11-21 から 22 にかけては、voice-switch が changelogmemo を直接書き換えていた（`changelogmemo-add`）。changelog スキルの編集と同じファイルを書くため、ロックを取らない相手と重なると項目が消えた。入れ替え・読み直し・時間の上限で 3 回直しても別の競合が出たので、書き手を分ける形に変えた。
