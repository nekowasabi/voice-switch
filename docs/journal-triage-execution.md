# 振り分けた依頼を実行する仕組み 設計

2026-11-21。前提は `docs/journal-triage-design.md`（分類器）。

## この設計で使う語

- 提案 = 分類器が依頼と判定した発話。実行するかどうかを決める前の状態
- 実行先 = 依頼の種類ごとに設定する、実行のやり方（URL を開く、POST、コマンド）。今の `macOS.actions` と同じ形
- 自動の印 = 実行先ごとの `auto: true`。付いた実行先だけ、承認なしで動く

## 目標と問題

- 目標: 話した依頼が実行まで進み、Python やターミナルを使わない人も voice-switch を入れるだけで使える。Mac と Windows で同じに動く。
- 問題: 今の分類はターミナルに一覧を出して終わる。実行する手段も、承認する画面も無い。Python のスクリプトなので、アプリから呼べず、配りにくい。

## 実行のきっかけの比較

| 候補 | 安全性 | 配りやすさ | 両 OS の手間 |
|---|---|---|---|
| メニューバーの提案画面で承認して実行 | 高い。#50 の「提案は自動、実行は承認制」をそのまま満たす | 高い。アプリに入っている | 分類器と画面を Swift と C# の両方に作る |
| 自動実行 | 低い。誤分類がそのまま外へ出る | 高い | 上と同じ実行部分を使えば、増えるのは印の判定だけ |
| 専用 CLI | 中くらい。承認の画面が無い | 低い。開発者向け | Python 1 本で済む |

## 推奨: アプリ内の提案画面を主にし、自動は実行先ごとの印、CLI は改善ループ専用

実行のやり方は 1 つにする。メニューから承認しても、自動の印で動いても、同じ実行部分（今の `WakeAction` の open / post / command）を通る。

### 流れ（起きる順）

1. 発話が履歴に入り、ジャーナルに書かれる（今のまま）。
2. 一覧に出る行（配送先が history か null）なら、アプリが裏で分類器を動かす。録音と次の入力は待たせない。直前 60 秒の発話はメモリの履歴から取る。
3. 行き先が `action:<種類>` なら、提案を作る。実行先にその種類が設定されていなければ、提案にせず一覧に残すだけにする。
4. 実行先に自動の印があれば、すぐ実行する。無ければ提案画面に載せ、メニューバーのアイコンに件数を出す。
5. 提案画面で、提案ごとに「実行」「却下」「種類を直す」を選ぶ。種類を直すと、その結果がラベルとして保存され、改善ループの正解になる。
6. 実行の結果（成功・失敗）を記録する。同じ提案は 2 回実行しない。

### 設定（例）

```json
"dictation": {
  "triage": {
    "enabled": true,
    "routes": {
      "look_up":         {"url": "grokbot://prompt?text={text}"},
      "self_task":       {"command": "rtm add"},
      "computer_change": {"command": "claude-queue add", "auto": false}
    }
  }
}
```

- 実行先の書き方は `macOS.actions` と同じ（`url`、`tokenEnv` 付きの POST、標準入力で本文を受ける `command`）。読み込みと検証のコードもそれを使う。
- `auto` の既定は false。最初はどの実行先も承認制にする。
- `enabled` が false なら、分類器は動かず、Jev にも何も送らない。

### 持ち主

| 状態 | 持ち主 | 書く人 |
|---|---|---|
| 発話の原文 | ジャーナル | アプリ（今のまま） |
| Jev の答え | 端末ごとのキャッシュ | アプリの分類器 |
| 提案の状態（待ち・実行済み・却下・失敗） | `~/Library/Application Support/voice-switch/proposals.jsonl`（Windows は `%LOCALAPPDATA%\voice-switch\`）。追記だけで、id ごとの最後の行が今の状態 | アプリだけ |
| ラベル | `<root>/.triage/labels/<端末>-app.jsonl` | アプリの提案画面だけ |
| ラベル（まとめて付けるとき） | `<root>/.triage/labels/<端末>-cli.jsonl` | CLI の `review` だけ |
| しきい値 | `<root>/.triage/thresholds.json` | CLI の `tune --apply` だけ |
| 問いの文面 | `Resources/triage_questions.json`（1 つのファイル） | 人が編集する。Swift・C#・Python が同じファイルを読む |

### 3 つの言語でそろえるもの

- 問いの文面は JSON 1 つにして、Swift・C#・Python が読む。今の `scripts/triage_questions.py` はこの JSON に移す。
- 真理値表は Swift と C# と Python の 3 か所に書くことになる。`tests/parity/fixtures/triage_decide.json` に「答え → 行き先」の見本を全組み合わせで置き、3 つが同じ結果を出すことを確かめる（今の `pane_route.json` と同じ作り）。

### CLI の役目

`scripts/journal_triage.py` は、改善ループの道具として残す。担当は、まとめての見直し（`review`）、精度の計測（`eval`）、しきい値の調整（`tune`）、問いの比較（`eval --candidate`）。実行はしない。保守する人向けで、利用者は使わなくてよい。

## 守る規則（検証項目の候補）

- E1 承認の無い提案は、自動の印が無ければ実行されない。
- E2 却下した提案は、どの順で操作しても実行されない。
- E3 同じ提案は 1 回しか実行されない（再起動・二重クリック・自動と手動の重なりを含む）。
- E4 実行先が設定されていない種類は、提案にならない。
- E5 `enabled` が false なら、Jev への送信は 0 件。
- E6 実行は既存の実行部分だけを通る。

E1〜E3 は順番の問題なので、TLA+ でモデルを作り、壊し版で落ちることを示す（このリポジトリの `verify-meet-pause` などと同じやり方）。

## 進める順

1. 問いの文面を JSON に移し、真理値表の共通見本を作る。Python の分類器をそれに合わせる（今のプローブも動くまま）。
2. Mac: 分類器をアプリに入れ、提案画面と実行を作る。自動の印はまだ使わない。E1〜E6 を確かめる。
3. Mac: 提案画面からラベルを付けられるようにする。
4. 自動の印を有効にする。
5. Windows に移す。共通見本で Swift と同じ結果を確かめる。

## 決めること

1. この形（提案画面が主、自動は実行先ごとの印、CLI は改善専用）でよいか。
2. 種類ごとの実行先。look_up、self_task、write_text、computer_change のそれぞれを、何で実行するか（例: Grok Bot、タスク管理、エージェントへの依頼）。
3. Mac を先に作り、Windows はあとで移すか。

## 範囲外

- ペインへの送信。#48 の範囲で、提案の実行先にはしない。
- 自動録音の発話をアプリが Jev に送ることについての README の約束（README_ja.md:210）の書き換え。分類器をアプリに入れる時点で、文面を直す。
