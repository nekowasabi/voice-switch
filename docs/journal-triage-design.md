# 発話ジャーナルの分類器 設計

2026-11-21。対象は `scripts/journal_triage.py`。アプリ（Swift / C#）は変えない。

## この設計で使う語

- 帯 = Noul の確率の読み方。0.7 以上を「はい」、0.3 以下を「いいえ」、その間を「迷い」とする
- 行き先 = 判定の結果。`action:<種類>`（依頼）、`thought`（残す考え）、`filler`（中身の無い声）、`unjudged:<段>`（どの段で迷ったか）
- 派生ファイル = Jev の答えを発話の id ごとに保存するファイル。ジャーナルとは別に置く

## 目標と問題

- 目標: 話したことは原文のまま全部残し、そのうえで一つひとつを「中身の無い声」「残す考え」「実行してほしい依頼」に見分け、依頼なら種類まで決める。
- 問題: 今は task / research / draft / agent / none の 1 問で全部を決めている。none が「中身が無い」と「中身はあるが種類が分からない」を兼ねるので、曖昧な考えほどフィラーと同じ扱いになる。迷うと確かだった部分まで失う。

## 持ち主

| 状態 | 持ち主 | 書く人 |
|---|---|---|
| 発話の原文と文脈（id, timestamp, text, origin, delivery, focusApp, taskchute） | ジャーナル `<root>/<端末>/<日>.jsonl` | アプリだけ。分類器は読むだけ |
| Jev の答え（各問いの確率） | 派生ファイル `<root>/.triage/<端末>/<日>.jsonl`（id ごと 1 行） | 分類器だけ |
| 判定（どの行き先か） | コードの真理値表 `decide(answers)` | 保存しない。毎回答えから計算する |

判定を保存しないので、しきい値を変えても Jev を呼び直さずに全件を判定し直せる。ジャーナルから消えた id の派生行は、次の実行で消す（削除の伝播）。`<root>` 直下のドットで始まるフォルダは端末フォルダとして読まない。

## 比べた 2 つの形

どちらも、小さな問いを 1 回の要求に束ね（speculative fan-out）、行き先はコードの真理値表で決める。違うのは依頼の種類の問い方。

- 形 1（不採用）: 種類を 1 つの Choice で問う。1 つしか選べないので、「〜を調べられるようにして」のように「調べる」と「PC を変える」の両方に当たる発話で確率が割れ、どちらも弱くなる。#50 のレビューで出た単一ラベルの問題がそのまま残る。
- 形 2（採用）: 種類ごとに Noul を 1 問ずつ出す。それぞれが独立に「はい」になれるので、複数の種類に当たる発話は複数の依頼として残る。

段ごとに別の要求を出す形（カスケード）は取らない。問いは同じ状態を共有し、束ねたほうが安く、待ちも 1 回で済む。今の 1 問に「メモ」を足す案は、迷った発話の捨て先を移すだけで段が増えないので、比べる前に外した。

## Jev に渡す状態

```json
{
  "utterance": {"text": "…", "started": "自動 | ウェイク | 手動"},
  "context": {"app": "Ghostty", "task": "voice-switch 開発", "time": "15:48"},
  "previous": [{"text": "…", "minutes_before": 2}]
}
```

- `previous` は同じ端末で 5 分以内の直前 2 件まで。独り言は前の発話の続きであることが多く、単独では意図が読めないため。一覧に出る行（delivery が history か null）だけから取る。欄に貼った発話（paste など）は、一覧に出ない文なので送らない。
- アプリ名と作業名は名前だけを送る。pid、bundleId、id は送らない。
- 文脈を送るかどうかは利用者の判断が要る（「決めること」1）。送らない設定では `utterance` だけを送る。

## 問い（1 回の要求に 3 問）

| id | 型 | 問い | criteria |
|---|---|---|---|
| `is_filler` | Noul | `utterance.text` は、意味のある内容を持たない声だけか | true: 相づち・言いよどみ・言い直しの断片・雑音の誤認識・部屋の誰かへの短い呼びかけ（「うん」「えーと、あれ」「はいはい」）/ false: 短くても途中で切れていても、考え・気づき・計画・願い・疑問・指示が入っている（「駅の傘立て、いつも満杯だな」「明日の会議を 10 時にずらして」） |
| `wants_action` | Noul | `utterance.text` の話し手は、考えを残すだけでなく、何かが行われることを望んでいるか | true: 自分か PC か AI に何かをさせたい（「牛乳を買っておかないと」「この表を週ごとにまとめて」）/ false: 気づき・感想・考えを述べているだけ（「この坂、思ったより長いな」） |
| `kind_self_task` | Noul | `utterance.text` で、話し手が自分でやる作業を言っているか | true: 「牛乳を買っておかないと」 / false: 人や PC にさせたい、または考えを述べているだけ |
| `kind_look_up` | Noul | `utterance.text` で、話し手は何かの答えを調べて知りたいか | true: 「この電池の寿命はどれくらいなんだろう」 / false: 答えを知りたい問いが無い |
| `kind_write_text` | Noul | `utterance.text` で、話し手は送る文や文書の下書きを望んでいるか | true: 「大家さんへのお礼のメールを書かなきゃ」 / false: 文を作る依頼が無い |
| `kind_computer_change` | Noul | `utterance.text` で、話し手は PC や AI エージェントに設定・コード・ファイルを変えさせたいか | true: 「このスクリプトで祝日も数えられるようにして」 / false: PC や AI に変えさせたいものが無い |

- 問いはすべての発話に出す。`kind_*` は `wants_action` が「はい」のときだけコードが読む。
- 「中身があるか」ではなく「フィラーだけか」を問う。短い命令は「考え・思いつき」に見えにくく、「中身があるか」と問うと低く出やすいため。
- criteria の例はすべて作った文。利用者の実際の発話は較正の確認用に取っておき、criteria には入れない。
- none の選択肢は置かない。

## 判定（コードの真理値表）

Noul は 0.7 以上を「はい」、0.3 以下を「いいえ」、その間を「迷い」として読む。

| wants_action | is_filler | kind_* | 行き先 |
|---|---|---|---|
| はい | （問わない） | 「はい」が 1 つ以上 | `action:<種類>`（「はい」の種類をすべて） |
| はい | （問わない） | 「はい」が 0 個 | `unjudged:kind` |
| 迷い | （問わない） | — | `unjudged:intent` |
| いいえ | はい | — | `filler`（一覧に出さない。件数だけ出す） |
| いいえ | 迷い | — | `unjudged:content` |
| いいえ | いいえ | — | `thought` |
| 通信失敗・答えの形が不正 | | | `unjudged:error`（派生行を書かず、次回やり直す） |

- 依頼の判定を先に置く。`wants_action` が「はい」なら、`is_filler` が何であっても依頼として残す。`filler` になるのは「依頼ではない」かつ「フィラーだけ」がどちらも確かなときだけ。
- 通信失敗・不正な答え・キー無しは、決して `filler` にしない。
- キー無し・`--no-jev` のときは、今の目印で `action:<種類>` か `unjudged:no-jev` にする。目印でフィラーは判定しない。
- しきい値（0.7 / 0.3）は 1 か所の定数にまとめる。較正前の初期値。

## 一覧の出し方

```

### 依頼
- 10:02:11 · private · look_up, computer_change · Ghostty — このスクリプトで祝日の数も調べられるようにして
### 考え
- 12:40:05 · private · Firefox — この坂、思ったより長いな
### 未判定
- 15:20:30 · wsl · intent(0.55) · Ghostty — あのブランチ、もういらないかも
フィラー 3 件 / 読めなかった行 0 件
```

## 検証項目

- C1 真理値表に穴が無い: `wants_action` 3 帯 × `is_filler` 3 帯 × `kind_*` 4 問それぞれ 3 帯 × 通信の成否の全組み合わせで、行き先がちょうど 1 つに決まる。
- C2 `filler` になるのは、`wants_action` が「いいえ」かつ `is_filler` が「はい」のときだけ。通信失敗・不正な答え・キー無しは `filler` にならない。
- C3 送る状態は表の欄だけ。文脈を送らない設定では `utterance` だけ。
- C4 派生ファイルに答えがあり、問いの文面が同じなら、Jev を呼ばない。文面を変えたら呼び直す。
- C5 ジャーナルのバイトは変わらない。ジャーナルから消えた id の派生行は消える。
- C6 標準エラーに本文を出さない（今の T5）。

C1〜C6 は今の T1〜T6 と同じ作り（本物のスクリプトを全組み合わせで動かし、HTTP を差し替え、規則ごとの壊し版で落ちることを示す）で `verify-journal-append` に入れる。

## 進め方

1. 先に実データで問いを試す（プローブ）。網羅テストは配管の正しさしか見ないので、Jev の答えが正しい帯に入るかは確かめられない。11-20 と 11-21 の実発話 4〜5 件で、問いの言い回しの候補を同じ要求に並べて出し、答えを見比べる。キーは利用者のシェルにあるので、利用者が実行する。送るのは各発話の本文（文脈を送ると決めた場合はアプリ名・作業名・直前の発話も）。
2. 問いが固まったら、スクリプトと C1〜C6 を実装する。
3. 30〜40 件で較正する（次の節）。

## 実データでの較正

- 自分の発話 30〜40 件（フィラー、考え、依頼、曖昧なものを含む）に正解の行き先を付ける。
- 一番重い誤りは「中身のある発話が `filler` になる」こと。これが 0 件になるまで、しきい値ではなく問いと状態を直す。
- 次に「依頼が `thought` になる」率と `unjudged` の割合を見る。
- 実送信は利用者の許可を得てから。送る本文の範囲を先に示す。

## 決めること

1. 文脈（アプリ名・作業名・直前の発話）を Jev に送るか。送ると、今の「送るのは本文だけ」の規則（README、検証の T3、壊し版 `send-context`）を変えることになる。送る範囲は、名前とテキストだけ、直前の発話は一覧に出る行だけに限る。
2. 派生ファイルの置き場所。`~/repos/context-storage/voice-switch/` は他の端末も書くので、そこに置くと書き手が 1 つに決まらない。案は、端末ごとの `~/Library/Caches/voice-switch/triage/<端末>/<日>.jsonl`。答えは Jev から取り直せるので、消えても困らない。

## 範囲外

- 依頼の実行（提案トレイと承認）。行き先 `action:<種類>` までを作る。
- アプリ側の変更。ジャーナルの形は今のまま使う。
- 固有名の補正（音声認識の「ブロックボット」→「Grok Bot」など）。較正で誤りの原因になると分かったら、既知の名前の一覧を状態に足す。
